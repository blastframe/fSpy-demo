# Parity tests

The claim this repo makes is narrow and checkable: **the browser runs the
original fSpy solver untouched, so its camera solutions are bit-identical to the
desktop implementation.** This document describes the evidence.

## 1. How the reference values were produced

`tests/fixtures/oracle.json` was generated by running the *upstream* solver
(vendored sources, compiled by `tsc`, executed in Node — no browser, no port) on
the upstream test projects in `tests/fixtures/*.fspy`:

```
node tools/oracle.js tests/fixtures/*.fspy > tests/fixtures/oracle.json
```

(see `tools/oracle.js`; it decodes each project, reads the embedded image's real
pixel dimensions, calls `Solver.solve1VP`/`solve2VP` and dumps
`principalPoint`, `relativeFocalLength`, `horizontalFieldOfView`,
`verticalFieldOfView`, `vanishingPoints`, `vanishingPointAxes`, `viewTransform`
and `cameraTransform`).

## 2. Fixtures

| Project | Mode | Notes |
| --- | --- | --- |
| `defaults.fspy` | 2-VP | fSpy's own default project (also shipped as `assets/example.fspy`) |
| `1 vp control test.fspy` | 1-VP | 1-VP with sensor/aspect mismatch warning |
| `missing horizon.fspy` | 1-VP | horizon guide at the image edge |
| `pp problem landscape.fspy` | 2-VP | manual principal point, landscape |
| `pp problem.fspy` | 2-VP | **must fail**: `Rotation determinant 0.91824` |
| `quad-problem.fspy`, `quad-problem-2/3/4.fspy` | 2-VP | quad mode (VP2 derived from VP1 endpoints) |

Larger upstream fixtures (`canon5d_16mm.fspy`, `iphone6plus.fspy`,
`ref_distance_in_yards.fspy`, …) are 2–7 MB of mostly embedded JPEG; they were
validated locally during development but are not committed. To check them:

```
git clone https://github.com/perarnia/fSpy /tmp/fSpy
node tools/oracle.js /tmp/fSpy/test_data/*.fspy > /tmp/oracle-all.json
```

## 3. What is compared

For every fixture, the in-app **Verify** button and `npm test` compare, with a
tolerance of `1e-12`:

- `relativeFocalLength`
- `horizontalFieldOfView`
- `principalPoint.x`, `principalPoint.y`
- all 16 elements of `viewTransform`
- all 16 elements of `cameraTransform`
- `vanishingPointAxes` (exact string match)
- for the deliberate failure case: that the *same* error is produced

Current result: **9/9 fixtures match with Δ = 0.0** (exact floating-point
equality), including the reproduce-the-error case.

## 4. Additional checks

| Check | Assertion |
| --- | --- |
| `relative ↔ image plane` round trip | error `0` |
| `relative ↔ mirrored viewport` round trip | error `0` |
| `relative → absolute pixels` | exact |
| Synthetic 2-VP, axis pairs X/Y, X/Z, Y/Z | `relativeFocalLength` and `hFOV` recovered to `1e-9`; rotation orthonormal to `1e-12` with `det = +1` |
| Synthetic 2-VP vanishing points | equal the analytic guide intersections to `1e-12` image-plane units |
| Synthetic 2-VP axis assignment | `vanishingPointAxes` equals the requested pair |
| Synthetic 2-VP world origin | reprojects onto the origin control point, `0 px` error |
| Synthetic 2-VP reference distance | rescales the translation only (rotation Δ `0`, intrinsics unchanged, origin still `0 px`) |
| Synthetic 1-VP | `f = 2·focal/sensor`; derived second VP satisfies `(Fu−P)·(Fv−P) + f² = 0` (residual `0`); origin reprojects exactly |
| Zoom / pan / both sidebars | full camera JSON identical before, during and after |
| `.fspy` write → read | state JSON and image bytes identical |

Result: **35/35 checks pass**.

A note on reprojection metrics: line-only calibration provides **no independent
3D point correspondences**, so a "reprojection error in pixels" against arbitrary
world points would be meaningless (the scale is set by the reference distance and
the sign ambiguities are unresolved). What *is* meaningful — and what is asserted
— is that (a) vanishing points agree with their guide intersections, (b) the
world origin reprojects onto its guide, and (c) the solved rotation is a proper
orthonormal matrix.

## 5. Running the tests

```
npm install          # typescript, esbuild, jsdom
npm test             # Node: oracle parity + invariants (tests/run-tests.js)
npm run check:engine # verifies src/engine/fspy-engine.js matches vendor/
```

The same parity suite is available in the browser: the **Verify** toolbar button
re-runs the fixture comparisons against `tests/fixtures/oracle.json`.

## 6. Remaining differences from the desktop app

| Area | Difference | Impact |
| --- | --- | --- |
| Image loading | Browser decodes the embedded image; `image.width/height` come from the decoded bitmap, as in Electron | none |
| `Buffer` usage | Upstream's `image-state.ts` types `data` as a Node `Buffer`; the web app passes `null` (the solver never reads it) | none — type-only |
| Result-display preferences | Stored and round-tripped, but the readout widgets always show absolute principal point | cosmetic |
| Camera preset list | The web app exposes all presets present in the vendored `camera-presets.ts`; upstream also shows a "focal length" hint per preset, surfaced here only in 1-VP mode | cosmetic |
| Error surfacing | Upstream shows the first error in its result panel; the web app shows all errors in a banner and keeps the last valid overlay | cosmetic |
| Translation when calibration is degenerate | Upstream will happily divide by a near-zero handle distance and return huge/inf camera positions; the web app rejects non-finite cameras and reports a diagnostic instead of rendering `NaN` | stricter, intentional |
